# Backend Plan: FO Geomap Portal

## 1. Frontend Audit Summary

### Stack
- **Framework**: React 18 + TypeScript + Vite
- **UI**: TailwindCSS, Lucide icons
- **Routing**: React Router v6
- **Maps**: react-leaflet
- **State**: `useState`/`useEffect` only (no Redux/Zustand)
- **Build**: Vite, oxlint, tsc

### CRITICAL: No API Layer Exists
The entire frontend is **localStorage-only**. Zero `fetch` calls to a backend. The only external call is `fetch('https://nominatim.openstreetmap.org/reverse')` inside `NewProjectModal.tsx:305` for geocoding.

**localStorage keys used:**
| Key | Purpose | Structure |
|-----|---------|-----------|
| `auth_user` | Current logged-in user | `AuthUser` object |
| `admin_user` | Admin credentials | `AuthUser` object |
| `app_users` | Registered users | `AuthUser[]` array |
| `fo_projects` | All project data | `any[]` array |

### Auth Model (Frontend)
```typescript
interface AuthUser {
  username: string;
  fullName?: string;
  email?: string;
  companyName?: string;
  password: string;          // PLAINTEXT
  role: 'admin' | 'user';
  mustChangePassword: boolean;
}
```
- Roles: `admin` | `user` (simple string, 2 roles)
- Password comparison: plaintext `user.password === password`
- No JWT. Auth check is `localStorage.getItem('auth_user')`
- `mustChangePassword` flow: login → redirect to `/change-password` or `/change-credentials`

### Length Validation Logic (Frontend)
- **KMZ route length**: Haversine/Vincenty geodesic calculation on `[lat, lng]` coordinate array (Vincenty inverse formula in `calculateRouteLength`)
- **BoQ cable length**: Parsed from Excel "Panjang Jalur" label
- **Tolerance**: Hardcoded 50 meters (`isLengthMatch = lengthDifference <= 50`) — spec wants configurable `ROUTE_LENGTH_TOLERANCE_PERCENT=5`

### Price Validation Logic (Frontend)
- **KHS matching**: BoQ item `code` matched against KHS `productNo` field
- **Comparison**: `submittedPrice === standardPrice` (exact match)
- **No percentage-based tolerance** in frontend — spec wants configurable price tolerance

### KHS Excel Import (Frontend)
Columns expected: `ItemCategory`/`Kategori`, `ProductNo`/`Kode`, `ProductDesc`/`Deskripsi`, `ItemPrice`/`Harga`

### Key Mismatches: Frontend vs Spec

| Aspect | Frontend | Spec | Resolution |
|--------|----------|------|------------|
| Roles | `admin`, `user` | `ADMIN`, `VALIDATOR`, `VIEWER`, `TECHNICIAN` | Backend uses 4 roles; API response includes `frontendRole` mapping |
| Statuses | `PENDING`/`VERIFIED`/`REVISION`/`REJECTED` | `DRAFT`/`SUBMITTED`/`PROCESSING`/`NEED_REVIEW`/`VALIDATED`/`REJECTED` | Backend uses spec workflow; API includes `verificationStatus` for frontend |
| BoQ item fields | `code`, `qty`, `submittedPrice` | `itemCode`, `quantity`, `unitPrice` | Backend stores both; API response matches frontend field names |
| Auth | localStorage plaintext | JWT + bcrypt | Backend implements JWT/bcrypt; frontend adapts in Phase 0 |
| File parsing | Client-side (FileReader, jszip, xlsx) | Server-side | Backend takes over all parsing; frontend just uploads files |
| Geocoding | Nominatim (client-side) | Backend | Backend calls Nominatim; frontend receives result |

## 2. Design Decisions

### D1: Backend Location & Structure
- **Location**: `backend/` subdirectory within `F:\MAGANG\fo-geomap-portal`
- **Structure**: Standalone Node.js project with own `package.json`, `tsconfig.json`, `Dockerfile`
- **Rationale**: Matches deliverable spec; keeps backend/frontend decoupled for independent development and deployment

### D2: No PostGIS (Resolved)
- Store geometry as `JSONB` (GeoJSON format) in PostgreSQL
- Use `turf.js` for all geodesic calculations (distance, line length)
- Can migrate to PostGIS later if advanced spatial queries are needed
- **Rationale**: User confirmed plain PostgreSQL + Turf.js

### D3: Roles
Backend implements 4 roles per spec: `ADMIN`, `VALIDATOR`, `VIEWER`, `TECHNICIAN`.
Mapping to frontend's 2-role model in API responses:
- `ADMIN` → frontend `admin`
- `VALIDATOR` → frontend `admin` (validators have same access as admin in frontend)
- `TECHNICIAN` → frontend `user`
- `VIEWER` → frontend `user`

### D4: Project Status Workflow
Backend uses spec's full lifecycle:
```
DRAFT → SUBMITTED → PROCESSING → NEED_REVIEW → VALIDATED
                                              → REJECTED
NEED_REVIEW → REVISION → VALIDATED/REJECTED
```
API responses include:
- `status`: spec status value (source of truth)
- `verificationStatus`: frontend-compatible value (`PENDING` = NEED_REVIEW, `VERIFIED` = VALIDATED, `REVISION`, `REJECTED`)

### D5: File Parsing — Server-Side
All file parsing (KMZ, BoQ Excel, KHS Excel) happens server-side. Frontend only uploads raw files via multipart/form-data.

### D6: Geocoding — Server-Side
Backend calls Nominatim during project submit/processing. Frontend receives province/city in the response.

### D7: Frontend Integration
- **Phase 0 (frontend)**: Minimal changes — create `src/services/api.ts` service layer, replace `localStorage` calls with API calls, update role/status handling
- **Approach**: Backend API shapes will be compatible with frontend's expected data where possible, with adapter fields for mismatches

### D8: Environment Variables
All configurable values via `.env`:
- Tolerance percentages (length, price)
- File size limits
- JWT secret/expiration
- Nominatim user-agent (required by Nominatim policy)

### Key Schema Notes

1. **UUID primary keys** on all tables (not auto-increment) for distributed safety
2. **Project.code** auto-generated as `PRJ-YYYY-XXXX` (year-sequence format)
3. **KmzRoute.lengthKm** stored in km, **LengthValidation** in meters (matches frontend's meter-based comparison)
4. **BoqItem.quantity** as Float (can be fractional, e.g., 0.5 KM of cable)
5. **PriceValidation** links BoqItem to KhsItem; NULL khsItemId means item not found in KHS
6. **KhsItem.itemCode** must match BoqItem.itemCode for price validation
7. **JSONB** for geometry data (GeoJSON) — no PostGIS
8. **ValidationStatus** enum used across length/price validations: MATCH, DIFFERENT, NOT_FOUND, NEED_REVIEW

## 5. Business Rule Mapping

### Rule 1: KMZ is source of truth for route length
- Backend parses KMZ using `kml-parser` + `turf.js` for geodesic distance
- Stores route coordinates as GeoJSON LineString in `kmz_routes.length_km`
- This replaces frontend's `calculateRouteLength` function

### Rule 2: BoQ is source of truth for quantity/price
- Backend parses BoQ Excel using `exceljs` with dynamic header detection
- Extracts: project name, cable length ("Panjang Jalur"), total value ("Total Harga"), items (KHS_ prefixed codes)
- This replaces frontend's `parseBoqExcel` function

### Rule 3: KHS is source of price reference
- KHS items stored in `khs_items` table
- BoQ `itemCode` matched against KHS `itemCode` (not `productNo` — unified to `itemCode` in backend)

### Rule 4: Price must be compared with KHS (not just code existence)
- For each BoQ item: look up KHS by `itemCode`
- If found: compare `unitPrice` vs `referencePrice`
  - Exact match → `MATCH`
  - Different → `DIFFERENT`
- If not found → `NOT_FOUND`

### Rule 5: NOT_FOUND for missing KHS items
- `price_validations.status = NOT_FOUND` when `khsItemId` is NULL

### Rule 6: DIFFERENT with full breakdown
- Backend returns `boqPrice`, `khsPrice`, `difference`, `differencePercentage` for mismatched items

### Rule 7: Configurable length tolerance
- `ROUTE_LENGTH_TOLERANCE_PERCENT=5` (environment variable)
- If `diffPercentage <= tolerance` → `MATCH`
- Else → `NEED_REVIEW`

### Rule 8: Project VALIDATED only when all validations complete
- `Project.overallStatus` = `VALIDATED` when:
  - Length validation: `MATCH` or `NEED_REVIEW` (approved by validator)
  - Price validation: all items `MATCH` or `DIFFERENT` (approved by validator)
- `verificationStatus` for frontend:
  - `PROCESSING` → (no frontend equivalent, frontend shows PENDING during processing)
  - `NEED_REVIEW` → frontend `PENDING`
  - `VALIDATED` → frontend `VERIFIED`
  - `REJECTED` → frontend `REJECTED`
  - `REVISION` → frontend `REVISION`

### Rule 9: Audit log for all status changes
- Every status transition logged in `audit_logs` with `action`, `oldStatus`, `newStatus`, `userId`, `ipAddress`

## 7. Frontend Integration Approach

### 7.1 Auth Flow Migration
**Current**: localStorage `auth_user` → `authService` functions
**Target**: Login → `POST /api/auth/login` → JWT stored in httpOnly cookie → all requests include cookie automatically

Frontend changes needed:
1. Create `src/services/api.ts` with `fetch` wrapper that includes credentials
2. Replace `authService` functions with API calls
3. LoginPage: call `POST /api/auth/login`, store JWT in cookie (not localStorage)
4. App.tsx `PrivateRoute`: replace `localStorage.getItem('auth_user')` with `GET /api/auth/me`
5. MainLayout: replace `getCurrentUser()` with API call
6. Logout: `POST /api/auth/logout` (clears cookie)

### 7.2 Project Data Migration
**Current**: `localStorage.fo_projects` array
**Target**: `GET /api/projects` (with role-based filtering)

Frontend changes:
1. ProjectListPage: fetch from API, maintain local search/filter state
2. UserDashboardPage: fetch from `GET /api/projects/mine`
3. VerificationDetailPage: fetch from `GET /api/projects/:id`, update status via `POST /api/projects/:id/validate`
4. NewProjectModal: replace client-side parsing with `POST /api/projects` (upload files)
5. GeomapPage: fetch GeoJSON from `GET /api/geomap/projects`

### 7.3 Status Mapping
Backend `status` → Frontend display:
```
DRAFT → (frontend doesn't show, only shows after submit)
SUBMITTED → (processing, frontend shows loading)
PROCESSING → (frontend shows loading)
NEED_REVIEW → PENDING
VALIDATED → VERIFIED
REJECTED → REJECTED
REVISION → REVISION
```
The API response includes both `status` (backend) and `verificationStatus` (frontend-compatible).

### 7.4 Role Mapping
Backend `role` → Frontend:
```
ADMIN → admin
VALIDATOR → admin
TECHNICIAN → user
VIEWER → user
```
The API response includes both `role` (backend) and `frontendRole` (compatible value).

## 11. Risks & Mitigations

| Risk | Mitigation |
|------|-----------|
| Windows path length limits | Use short `storage/` paths, UUID filenames |
| Nominatim rate limits | Backend handles geocoding (not frontend); add retry with delay |
| Excel format variations | Robust header detection (case-insensitive, multiple label aliases) — replicate frontend's dynamic search approach |
| KMZ parsing errors | Graceful fallback: empty route, length=0, error logged |
| Large file uploads | Multer stream + size limit; queue for async processing if needed |
| Role mismatch (2→4) | `frontendRole` field in auth response for gradual migration |
| Status mismatch | `verificationStatus` field in API response for frontend compatibility |
| Password migration (plaintext→bcrypt) | Seed new bcrypt passwords; admin can reset |
